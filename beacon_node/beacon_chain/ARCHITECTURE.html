The Problem Why

BeaconChain<T> is a single struct with 40+ fields. Every caller holds Arc<BeaconChain> and can reach everything. This makes it hard to test in isolation, hard for LLMs to reason about, and hard to iterate on without risk.

After — Components + Composition

BeaconChain is replaced by focused components. Callers hold refs but no logic — logic lives in the components and composed workflow functions.

As LLMs improve, the proportion of work they can handle grows — but only if the codebase is structured for it. A god object is a ceiling. Modular components are a foundation that scales with model capability.

Design Principles Constraints

Derived from specific problems in the current BeaconChain<T>. Not prescriptive — these guide design decisions.

1

Favour composition over god objects

Workflows compose the specific capabilities they need — not whole components. Pass what you need, not what has what you need.

Today produce_block_on_state accesses self.* for everything because the god object makes it easy. Tracing what it actually uses reveals 3 domain dependencies out of 40+ fields. See the block production case study below.
2

Separate business logic from infrastructure

Components own verification logic and state. Infrastructure like chain state, current slot, and event dispatch is provided by the caller — either as values, references, or callbacks.

Today verification methods internally reach into CanonicalHead for head state and SlotClock for the current epoch. This couples every component to chain infrastructure and makes isolated testing impossible. For example, the caller could read slot_clock.now() and pass the resulting Epoch in, or pass a callback for mid-workflow side effects like SSE events.
3

Components are testable in isolation

You should be able to construct a component, pass in test state, and assert results — without BeaconChainHarness, store, or fork choice.

Today you can't test verification logic without spinning up the full chain. Deterministic components that receive context as parameters can be tested directly, verified against specs, and safely modified by LLMs.
4

Fork choice write locks are concentrated

Fork choice write locks are acquired only by block import, head recomputation, attestation application, and execution layer callbacks. Components like OperationsManager and SyncCommitteeManager never touch them.

The lock ordering in canonical_head.rs is where deadlocks happen. Today any code holding Arc<BeaconChain> can reach the fork choice lock. No fork choice write locks exist outside beacon_chain — this architecture enforces that.

BeaconChain is fully replaced. Components own the logic. Callers hold refs to components but no logic of their own.

Case Study: Block Production Composition

produce_block_on_state looks like it needs the entire BeaconChain. It doesn't. Tracing the actual code reveals three domain dependencies — the rest is infrastructure.

What block production actually needs

Today produce_block_on_state accesses self.* everywhere because the god object makes it easy. But tracing what it actually uses:

Domain &OperationPool Pull attestations, exits, slashings, sync aggregate, BLS changes CanonicalHead Head slot, finalized checkpoint, forkchoice params (read-only) ExecutionLayer Get payload from EL, fee recipient, gas limit Infrastructure &ChainSpec Spec constants (everything needs this) BlockProductionConfig ~5 flags: paranoid mode, size limits, builder fallback SlotClock Current slot TaskExecutor Spawn blocking work

3 domain dependencies vs 40+ fields on the god object. The infrastructure deps (spec, clock, executor) are just Rust requiring you to be explicit about what other languages grab from globals.

Composed block producer — code sketch
block_producer.rs — composed from thin slices 
/// Block production composed from the minimum interface it needs.
/// No Arc<BeaconChain>, no god object.
pub async fn produce_block(
    state: BeaconState<E>,
    // Domain dependencies (the actual coupling)
    op_pool: &OperationPool<E>,
    canonical_head: &CanonicalHead<T>,
    execution_layer: &ExecutionLayer<E>,
    // Infrastructure (spec, config, clock)
    spec: &ChainSpec,
    config: &BlockProductionConfig,
    slot_clock: &T::SlotClock,
) -> Result<BeaconBlock<E>> {
    // 1. Pack operations from pool
    let attestations = op_pool.get_attestations(&state, spec)?;
    let (slashings, exits) = op_pool.get_slashings_and_exits(&state, spec);

    // 2. Check chain health for builder fallback
    let health = check_chain_health(canonical_head, slot_clock, config);

    // 3. Get execution payload
    let payload = execution_layer.get_payload(
        canonical_head.forkchoice_update_params(),
        health.use_builder(),
    ).await?;

    // 4. Assemble block
    assemble_block(state, attestations, slashings, exits, payload, spec)
}
Testing without the harness

Because produce_block takes thin slices, you can test it directly with constructed state and mock pools. No BeaconChainHarness needed.

test — block production packs available operations 
#[tokio::test]
async fn block_includes_available_exits() {
    let spec = ChainSpec::mainnet();
    let (state, keypairs) = create_genesis_state(&spec, 16);

    // Set up an op pool with one voluntary exit
    let op_pool = OperationPool::new();
    let exit = make_signed_exit(&keypairs[0], 0, Epoch::new(5), &spec);
    op_pool.insert_voluntary_exit(exit.clone());

    // Mock execution layer and canonical head
    let mock_el = MockExecutionLayer::default_payload();
    let mock_head = MockCanonicalHead::at_slot(10);

    let block = produce_block(
        state, &op_pool, &mock_head, &mock_el,
        &spec, &BlockProductionConfig::default(), &test_clock(),
    ).await.unwrap();

    assert_eq!(block.body().voluntary_exits().len(), 1);
    assert_eq!(block.body().voluntary_exits()[0], exit);
}

Spec-Driven Development Exploring

The modular architecture opens the door to spec-driven workflows: humans define behavior and correctness properties upfront, LLMs implement against them. We're exploring two complementary approaches.

✍

Scenario Specs

Behavior & alignment

Quick to draft, easy to iterate on, readable by anyone. Good for aligning on feature behavior and happy-path scenarios at the start of a feature. Less suited for exhaustive correctness.

🔎

Formal Specs

Mathematically proven invariants

Machine-checkable proofs that properties hold for all inputs — not just specific scenarios. No ambiguity, no interpretation. Covers state machine invariants, consensus constraints, and correctness properties that scenarios and natural language can't reliably capture.

Complementary, not competing: Scenario specs map out behavior quickly — "given X, when Y, then Z". Formal specs mathematically prove what scenarios can't exhaustively cover — no ambiguity, no interpretation, machine-checked. Both feed into LLM-generated implementations and tests. The workflow between them is still being figured out.

Examples

scenario spec — quick to draft, easy to align on 
Feature: Voluntary Exit Verification

  Scenario: Valid exit is accepted
    Given a genesis state with 8 validators
    When validator 0 submits a voluntary exit at epoch 5
    Then the exit is accepted as new

  Scenario: Duplicate exit is ignored
    Given a genesis state with 8 validators
    And validator 0 has already submitted a voluntary exit
    When validator 0 submits the same exit again
    Then the exit is marked as already known

  Scenario: Exit for unknown validator is rejected
    Given a genesis state with 4 validators
    When validator 999 submits a voluntary exit
    Then the exit is rejected with an error
formal spec (Lean 4) — machine-checked, compiler verifies the proof 
-- Model the observation logic, then prove idempotency:
-- "if verify_and_observe returns New, a second call must return AlreadyKnown"

def verify_and_observe (seen : Finset Nat) (idx n : Nat)
    : Outcome × Finset Nat :=
  if idx ≥ n then (.InvalidIndex, seen)
  else if idx ∈ seen then (.AlreadyKnown, seen)
  else (.New, seen ∪ {idx})

theorem idempotent (seen : Finset Nat) (idx n : Nat)
    (h : (verify_and_observe seen idx n).1 = .New) :
    (verify_and_observe (verify_and_observe seen idx n).2 idx n).1
      = .AlreadyKnown := by
  simp [verify_and_observe] at h ⊢
  split <;> simp_all [Finset.mem_union, Finset.mem_singleton]

#[test]
fn rejects_exit_for_unknown_validator() {

Results Status

Seven components extracted, ~2,000 lines of new unit tests, full CI green, and a local testnet that produces blocks and finalises. The top-level type shrank from 7,317 to 1,025 lines and lost its 200+ methods. Two scoped orchestrators and a slim top-level type are the next steps.

What worked

  • Seven components extracted; four cohesive. OperationsManager, AttestationManager, SyncCommitteeManager, and ValidatorQueryService came out as self-contained units with clear ownership of their observed sets and pools. DataAvailabilityManager, ExecutionManager, BlockImportState extracted too but are thinner wrappers.
  • ~2,000 lines of new unit tests against those components, written without BeaconChainHarness. This is the concrete contributor-velocity win — tests that construct components directly, pass in state, and assert results.
  • Proved the seams. Once components owned their observed sets and pools, the shape of a scoped BlockImporter<T> / BlockProducer<T> became obvious — which is the active follow-up work.
  • Top-level file shrank from 7,317 to 1,025 lines. beacon_chain.rs → beacon_components.rs. The remainder is struct definition, builder plumbing, and a few cross-component helpers.

What to revise (in progress)

  • BeaconComponents<T> has ~40 pub fields. Zero methods, but the coupling is unchanged — every caller that used to say chain.field still says components.field. Being fixed by slimming to BeaconSystem<T> with only Arc<Component> fields.
  • 254+ call sites build *Context literals. In block_production/mod.rs, a 12-field BlockProductionContext literal is constructed four times in one function. Being fixed by extracting BlockImporter<T> and BlockProducer<T> as scoped structs that own their Arcs.
  • Duplicate Arc paths to the same data. chain.op_pool and chain.operations_manager.op_pool resolve to the same pool, with // migrate later markers. Being fixed by routing all callers through the owning component.
  • Orchestrator files didn't shrink, just moved. block_import_methods.rs is 2,022 lines, block_production/mod.rs is 1,692. Being fixed by folding them into impl BlockImporter<T> / impl BlockProducer<T>.
  • Trading &self for &chain + 12-field struct was lateral. Rust's idiomatic DI is struct holds its Arcs, methods use &self — constructor injection. The follow-up work moves to that pattern.

Quick Reference Cheat Sheet

Patterns and anti-patterns for developing in the modular architecture.

Adding a New Verification

Add method to the relevant component with state as params
Have the caller fetch state and pass it in
Return result; let caller handle side effects
Fetch state internally from the component
Emit events or log metrics from inside the component

Adding a New Component

Minimize generic parameters — only what you actually need
Register in the Builder, wire refs to callers
Write unit tests with constructed state
Add type parameters "just in case"
Hold references to shared mutable state

Testing a Component

Construct the component directly
Create test state and pass it as parameters
Write a scenario spec first for alignment
Use the full harness for unit-level tests
Set up store, fork choice, or networking

Cross-Component Coordination

Keep dependencies one-directional
Coordinate via composed workflow functions
Follow documented lock ordering
Create circular dependencies between components
Acquire write locks from within a component
