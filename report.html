The Problem

BeaconChain<T> is a god object: 40+ fields, 200+ methods, 7317 lines in a single file. Every concern — attestations, sync committees, data availability, execution layer, block production — is tangled into one struct. This makes the codebase hard to reason about, hard to test, and impossible for LLMs to safely modify one concern without understanding everything.

Why it matters: A god object forces every contributor — human or LLM — to hold the entire system in their head. An LLM can't safely implement an attestation pool change without understanding block import locking, execution layer callbacks, and dozens of other unrelated concerns. Modularization draws clean boundaries so each concern is self-contained, testable, and safe to work on in isolation.

How We Work

The modular architecture enables a productive division of labor. Humans own the hard problems — architecture design, specification, and correctness review. LLMs handle the volume work — implementation, test generation, and fast iteration across components.

Humans

  • Design component boundaries and data flow
  • Write scenario specs (Given/When/Then) and formal invariants
  • Review every PR for correctness, liveness, and lock safety
  • Own consensus-critical decisions and fork choice lock ordering
  • Define migration strategy for cherry-picking upstream commits

LLMs

  • Implement component methods against explicit specs
  • Generate unit tests — construct with ::new(), no harness
  • Migrate callers: replace chain.method() with direct component access
  • Refactor: extract fields, move methods, update 60+ call sites
  • Iterate quickly: change internals, test in isolation, repeat
The prerequisite is the architecture. An LLM can implement OperationsManager::verify_voluntary_exit() correctly because its parameters are explicit and its scope is narrow. It cannot safely modify a 7317-line god object method that reads 15 fields and acquires 3 locks.

Design Principles

1

Favour composition over god objects

Workflows compose the specific capabilities they need — not whole components. Pass what you need, not what has what you need. Block production needs 3 domain dependencies out of 40+ fields; the composed function takes exactly those 3.

2

Separate business logic from infrastructure

Components own verification logic and state. Infrastructure like chain state, current slot, and event dispatch is provided by the caller — either as values, references, or callbacks. The caller reads slot_clock.now() and passes the resulting Epoch in.

3

Components are testable in isolation

Construct a component with ::new(), pass in test state, and assert results — without BeaconChainHarness, store, or fork choice. No slot processing, no database, no network. Tests run in milliseconds.

4

Fork choice write locks are concentrated

Fork choice write locks are acquired only in block import, head recomputation, attestation application, and execution layer callbacks. Components like OperationsManager, SyncCommitteeManager, and ValidatorQueryService never touch fork choice locks. This preserves the lock ordering documented in canonical_head.rs.

Structure

BeaconComponents<T> is a pure ref-holder with zero methods. Components own state and logic. Callers (HTTP API, NetworkBeaconProcessor, Sync Manager) hold Arc refs to components and contain no business logic of their own.

Case Study: Block Production

Today, produce_block_on_state accesses self.* for everything because the god object makes it easy. Tracing what it actually uses reveals 3 domain dependencies out of 40+ fields. The remaining dependencies are infrastructure (&ChainSpec, SlotClock, TaskExecutor) that every async workflow needs.

Dependency What it uses
&OperationPool Pull attestations, exits, slashings, sync aggregate
CanonicalHead (read) Head slot, finalized checkpoint, forkchoice params
ExecutionLayer Fee recipient, gas limit, get_payload

The composed function takes exactly those 3 dependencies — no Arc<BeaconChain>, no god object:

/// Block production composed from thin slices. /// No Arc<BeaconChain>, no god object. pub async fn produce_block( state: BeaconState<E>, // Domain dependencies (the actual coupling) op_pool: &OperationPool<E>, canonical_head: &CanonicalHead<T>, execution_layer: &ExecutionLayer<E>, // Infrastructure spec: &ChainSpec, config: &BlockProductionConfig, slot_clock: &T::SlotClock, ) -> Result<BeaconBlock<E>> { let attestations = op_pool.get_attestations(&state, spec)?; let (slashings, exits) = op_pool.get_slashings_and_exits(&state, spec); let health = check_chain_health(canonical_head, slot_clock, config); let payload = execution_layer.get_payload( canonical_head.forkchoice_update_params(), health.use_builder(), ).await?; assemble_block(state, attestations, slashings, exits, payload, spec) }
This is the core pattern. Every complex call site — block import, the HTTP API, sync — composes the thin slices it needs. Each function signature documents exactly which components it depends on. An LLM can implement or modify any of these functions without understanding the rest of the system.

Spec-Driven Development

Tests read as specifications. Each test name describes a scenario and expected outcome. Inside the body, Given/When/Then comments mark phases so any reader — human or LLM — can follow the intent.

Test naming convention

// Pattern: <verb>_<scenario>[_<expected_outcome>] valid_exit_accepted() duplicate_exit_returns_already_known() exit_different_validator_accepted() invalid_exit_bad_signature_rejected() shuffling_is_compatible_matching_shuffling() get_aggregated_attestation_rejects_optimistic_block()

Real BDD test from attestation_manager/tests.rs

#[test] fn given_multiple_committees_when_attestations_inserted_then_each_retrievable() { // Given an AttestationManager let manager = make_manager(); let spec = make_spec(); let slot = Slot::new(1); let block_root = Hash256::repeat_byte(0xaa); // When we insert attestations from two different committees let att_committee_0 = make_attestation(&spec, slot, block_root, 0); let att_committee_1 = make_attestation(&spec, slot, block_root, 1); manager.add_to_naive_aggregation_pool(att_committee_0.to_ref()) .expect("committee 0 insert should succeed"); manager.add_to_naive_aggregation_pool(att_committee_1.to_ref()) .expect("committee 1 insert should succeed"); // Then the pool contains both attestations let pool = manager.naive_aggregation_pool.read(); assert_eq!(pool.iter().count(), 2, "pool should contain attestations from both committees"); }
No BeaconChainHarness. The test constructs AttestationManager directly with make_manager(), inserts attestations from two committees, and verifies the pool holds both. No fork choice, no database, no network. This test runs in milliseconds and an LLM can write it from a one-line scenario spec.

What Changed

  • 6 component structs extracted from BeaconChain — OperationsManager, AttestationManager, SyncCommitteeManager, DataAvailabilityManager, ExecutionManager, ValidatorQueryService. Each owns its state and is constructable with ::new().
  • Attestation verification decoupled — all 26 call sites migrated from &BeaconChain<T> to AttestationVerificationContext.
  • Block import and production converted to free functions — 9 block import helpers and 7 block production helpers use explicit context structs.
  • 15 state query methods extracted to free functions in state_query.rs, taking (store, canonical_head, spec) as explicit parameters.
  • Drop persistence moved to components — OperationsManager, CanonicalHead, and DataAvailabilityManager each persist their own state on drop.
  • 17 thin wrapper methods deleted, 60+ callers migrated across http_api and network crates to direct component access.
  • with_committee_cache deduplicated from 3 implementations to 1 on AttestationManager.
  • Struct renamed from BeaconChain to BeaconComponents — zero impl methods in beacon_components.rs.

Reference: Core Pattern

Components own verification logic and state. Infrastructure is provided by the caller. Most verification follows a three-step pattern.

1. Fetch state
Caller gets head state, current epoch, fork choice data
2. Verify/process
Component runs business logic against that state
3. Mutate owned data
Component updates observed_*, pools, caches
// Component: pure logic + owned state, receives context as params impl<E: EthSpec> OperationsManager<E> { pub fn verify_voluntary_exit( &self, exit: SignedVoluntaryExit, head_state: &BeaconState<E>, wall_clock_epoch: Epoch, ) -> Result<ObservationOutcome<SignedVoluntaryExit, E>> { self.observed_voluntary_exits .lock() .verify_and_observe_at(exit, wall_clock_epoch, head_state, &self.spec) } } // Caller (e.g. gossip handler): fetches state, calls component fn handle_voluntary_exit( operations: &OperationsManager<E>, canonical_head: &CanonicalHead<T>, slot_clock: &T::SlotClock, event_handler: &Option<ServerSentEventHandler<E>>, exit: SignedVoluntaryExit, ) -> Result<()> { let head = canonical_head.cached_head(); let epoch = slot_clock.now().unwrap().epoch(E::slots_per_epoch()); let outcome = operations.verify_voluntary_exit( exit, &head.snapshot.beacon_state, epoch, )?; if let ObservationOutcome::New(ref verified) = outcome { if let Some(handler) = event_handler { handler.register(EventKind::VoluntaryExit(verified.clone().into_inner())); } } Ok(()) }

Cheat Sheet

Quick reference for working with the modularized beacon_chain crate.

Do
  • Put business logic in component methods with explicit parameters
  • Write unit tests that construct components with ::new()
  • Use context structs for cross-component orchestration
  • Pass values (Epoch, &BeaconState) not infrastructure (&SlotClock)
  • Use from_chain constructors for backward-compatible migration
  • Name tests as specifications: verb_scenario_outcome
  • Use Given/When/Then comments for non-trivial test bodies
  • Let components persist their own state on Drop
Don't
  • Add methods to impl BeaconChain<T> in beacon_chain.rs
  • Use BeaconChainHarness for unit tests of isolated logic
  • Acquire fork choice write locks outside block import / head recomputation
  • Pass &BeaconChain<T> to new functions — pass specific components
  • Fetch infrastructure state inside components (let the caller do it)
  • Add fields to BeaconComponents without assigning them to a component
  • Hold Arc<BeaconComponents> in new callers — hold individual component Arcs
  • Mix business logic with event dispatch / SSE emission

Where to put new code

Scenario Where to put it
Logic on a component's owned state Component method
Orchestration across multiple components Free function with a context struct
Cross-cutting infrastructure (per-slot tasks) impl BeaconChain<T> (rare, justify in PR)
